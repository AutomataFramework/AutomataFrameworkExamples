# Build

## Quality bar

The least every brief's acceptance criteria cover, where they apply:

- The core loop and the objectives and state transitions defined in the brief work. Where the game defines winning or losing, each outcome is clear and testable. Open-ended games use their specified progression and recovery criteria.
- The game handles restart, pause and save where it has them.
- Every game is fully playable with a keyboard alone and with a gamepad alone: every screen, menu and dialog, not only play itself, with a visible focus ring wherever the player is, and anything the player must type (a code, a name) can be entered with the pad. Each of the two has its own end-to-end walk (Playtest and controls check in `scene-polish`). The player can also use every supported control the brief names, such as mouse and touch.
- In the opening minute a new player knows what to do without being told.
- Meaningful actions have clear, appropriate feedback. Essential information remains understandable with audio muted; sound supports the experience where appropriate. Challenge and difficulty follow the brief.
- The game's audio and motion are consistent with its art direction, with no stutter, pops or clipping.
- The frame-time and loading budgets in the brief hold on the named hardware in the brief, measured.
- Browser device profiles emulate a screen size, a user agent and touch: that is emulation evidence, not proof of how a physical phone performs. A budget for a device is measured on that device.

## How code is written

- Comments say why. They do not say which plan asked for the code.
- Use injected clocks and fixed seeds. Browser tests wait on readiness, never on a sleep.
- A browser game detects a software renderer (the WebGL debug renderer name, such as SwiftShader) and then caps its frame rate and resolution, so browser tests in a container start in seconds instead of timing out; a real GPU is never capped. In PixiJS set both `ticker.maxFPS` and `ticker.minFPS`, since `maxFPS` is clamped to at least `minFPS`. A cap of one or two frames a second is enough for a test: a menu that took most of half a minute starts in a couple of seconds, and specs that open several pages run several times faster.
- With the frame cap on, input is still read on every animation frame; only the drawing is capped. Input read only in the capped render ticker misses presses: at one frame a second, gamepad taps fall between reads. The check: with the cap on, a test presses a key and taps a gamepad button (fake the pad by stubbing `navigator.getGamepads`), and the game sees each one through the same per-frame poll. Trigger: a diff that touches input code or the frame cap. The GPU path does not change.
- Specs that are visual evidence (screenshots, and passes that judge colour or motion) and the guard step that catches software WebGL run only on GPU pods, never on a CPU pod or GitHub's runners, and are left out of the local smoke set. On a CPU machine they time out even when run alone, and frames drawn at one frame a second and half resolution prove nothing. The check: a test reads the CI config and fails if a job that runs on a CPU machine would run a visual spec or the guard step. Trigger: a diff that adds a visual spec or changes the CI pieces.
- Keep a small smoke set: a handful of the main journeys, on the smallest and largest device, that passes in a cloud container in a few minutes. Run it before every push. A spec that opens several pages (one per player) runs one worker at a time on a CPU machine: parallel workers starve each other and fail on timeouts.
- Before speeding up the unit tests, measure where the time goes. The test runner reports its phases: loading the files (it may call this collect or import), building the environment, the setup files, and the test bodies. Loading often costs more than the tests themselves. Compare each phase to the time spent in the test bodies as a ratio, never as seconds alone, since the same suite takes very different time on two hosts ("CI and test machines" in `vertical-slice`). The ratio finds the cost and shows a fix worked; the change is still done only when real runs show it, as that section says. Trigger: a diff made to speed up the unit tests, or a unit-test job that has grown slow.
- A unit-test file with no DOM in it runs in a plain Node environment, and a DOM environment is built only for the files that need one, since building it is paid again in every file. A file moves to Node only when all three hold: it passes there without the DOM setup, nothing it loads checks for `window`, `document` or `navigator` (some libraries quietly switch to another mode when there is no window, so the test passes while testing something else), and it does not check for a window itself. A setup file fits the environment it runs in: with no window it skips the DOM stand-ins and does not import the DOM testing helpers, and under the DOM environment it does exactly what it did before. The check: a test fails when a Node file, or project code that file imports, names one of those globals, and a test runs each setup file with no window and fails if it throws or loads a DOM helper; a library a moved file imports is read for those globals once, when the file moves. Trigger: a diff that adds a unit-test file, moves one between environments or touches a test setup file.
- Fakes and mocks stay narrow: a test imports only the fakes it uses, each from its own file, never through a barrel file that drags in every screen, because every test file pays to load everything it imports. A generated catalogue of many small files (one file per translated message, for example) is loaded in tests as one module. Where that takes a test-only stand-in, a test proves the stand-in exports exactly the same names as the real generated files and gives the same result for each, and the build keeps using the real files. That test checks the stand-in, which is hand-written test code; the generated files themselves are still verified through their source and the tool that makes them (Verification below). Trigger: a diff that adds a shared fake, a file under `tests/` that re-exports other files, or a test-only stand-in for generated code.
- Look at the real expected, actual and diff images before accepting a visual change, and explain each change.
- A look that many screens share (a panel, a button, a chip) is one shared component with its values as named tokens, and a screen uses it instead of styling its own. A test fails on a second copy: it reads the styles, or the drawing code where menus are drawn on the canvas, and fails when any file but the shared component sets that look's fill, blur or border. A rule the owner sets for a look (every panel has the same finish, for example) is written as numbers the test and the reviewers measure, such as how much shows through and the text contrast, not judged by eye. The shared pieces live in one low feature that the screens import (the layout below), not in a top-level `components/`. Trigger: a diff that adds or restyles a screen.
- Two pieces of work that restyle the same screens or the same shared component touch the same files and the same assumption, so the later one starts from a `main` that holds the earlier one (Splitting in `staged-path`); a numbered order alone is not a reason to wait, a shared look is. Built the other way round, the later one's screens are rebuilt and walked again. Trigger: a plan or brief that restyles screens another open pull request also restyles.
- Code is grouped by feature, not by kind: no top-level `components/`, `services/` or `utils/`. A feature owns its code and data and imports only from features below it. Tests never sit beside the source; `tests/` mirrors `src/`. The layer order is written in `tests/architecture.test.ts`, one list with the lowest feature first, and the test fails on an upward import or a cycle.

  ```
  src/
    index.ts                 the public surface; anything it does not export is internal
    lib/                     shared helpers with no feature logic (maths, IO, random)
    features/<feature>/      one folder per feature: <feature>.ts is its entry, one job per file, library/ its data
  scripts/                   thin command-line wrappers over src/
  tests/                     mirrors src/; architecture.test.ts holds the layer rule (imports go down, no cycles)
    golden/                  pixel or snapshot goldens, one per scene
    playtest/                Playwright playthroughs of the whole game
  docs/superpowers/          specs/, audits/, live/, progress.md and history.md
    roadmap.md               everything left, in order, with who does it and where it stands
  ```

## Verification

Checks are what let work be handed off: what a program can judge, nobody has to read line by line. The owner says what done looks like and looks at the evidence; the checks do the rest, so they are built and kept like any other part of the product.

- **Run it like a person.** Before a change that alters what the product does is called done, its builder runs it: starts the app or game, goes through the changed journey with real taps, clicks, keys and typing, and looks at what happens. Passing tests are not this. How to start and drive this repo is in its `verify` skill, which the builder loads before every commit that changes behavior. Every session leans on it, so it stays quick and steady: a step in it that breaks or flakes is fixed first, and a change to how the product starts or what its first screen shows updates it in the same pull request. A session starts it clean once; its later runs may reuse the app or game it already has running.
- **The test that is hardest to fool comes first.** A unit test can pass while the feature is broken, because the test and the code share the same misunderstanding. So, in this order: 1. **Journeys**: a person's path through the running product, from the first screen to done; a failure names the step, with a screenshot; a changed journey gets a journey test. 2. **Property tests**, for the cases people and agents both miss: state something that must always hold and let many generated inputs, from a fixed seed, try to break it: round trips (save then load gives back the same thing), invariants (a count never goes below zero), repeats (doing it twice is the same as doing it once: migrations, retries, clean-ups) and twins (a fast version agrees with a plain, correct one). A property-test library is a new dependency and needs the owner's yes first. 3. **Old-versus-new tests**, for a rewrite or a move that should not change behavior: run the old and the new on the same inputs, set aside differences that do not matter (spacing, order), and treat every other difference as a bug unless it is on the change's written list of intended differences. Unit tests cover the small pieces underneath.
- **Test first, from the outside in.** Write the failing test first and confirm it fails for the right reason. The first one is the hardest-to-fool test the change reaches: a journey test when the change alters a journey, a property test when a rule must always hold. It stays failing while small unit tests build the pieces under it, each in a quick loop: a failing test, the least code that passes it, then a tidy-up with every test still passing.
- **Old code and today's behavior.** A test that pins what the code does today, before a refactor or a rewrite, passes at once on purpose: show that it can fail by breaking the code on purpose, then put the code back. Code written before its test is thrown away and written again from the test, except the old code in a rewrite, which stays as the yardstick until the old-versus-new test passes on the new.
- **Tests.** Quick targeted tests run locally whenever they help; CI is the merge gate. A failing test blocks only the change that touches it: report an unrelated failure, and give a failure on `main` its own thread. A merge still needs every required check green, unless the owner authorizes an exception named in the pull request. Never loosen, skip or re-record a test to hide a defect. No `--pass-with-no-tests` or similar flag that lets an empty suite pass in CI. Updating a golden for an approved behavior change is fine, with its before and after shown. A docs change or a purely visual change is verified by what fits (a link or build check, the approved look), a configuration change by lint, typecheck, the build and the CI run, and generated code (an API report, compiled messages, a database client) through its source and the tool that makes it, not by an invented unit test.
- **Quick and steady, or it gets skipped.** A slow check gets run less, and a flaky one teaches a session to rerun instead of fix. Cheap checks first (lint, typecheck, the tests the change reaches); before a push, the journeys the change reaches; the full suite in CI, where `release` sets the gate. A test that fails once and passes on retry is a defect. One rerun to find out whether a failure is flaky is allowed, and both results are reported; that rerun does not count as the clean run lane 2 needs. Report the flaky test with its text and record it under "Flaky tests" in `docs/superpowers/history.md`; its root cause is fixed in its own thread, unless it blocks this change. Never rerun it until it passes, slow it with a sleep, or skip it. If the root cause is not found within the tries in Settings, delete the test (never one for authorization, privacy, migrations or concurrency: that one stays and its root cause is found), put a steady check of the same thing in its place where one can be written, and record why, and the gap it leaves, under "Flaky tests".
- **A change does not quietly edit its own check.** If a change can edit the check that judges it, the check proves little. So CI workflow files, the repo's own root `CLAUDE.md` and the shared skills (every skill in `.claude/skills/` but `verify` and `this-repo`) change only in a pull request that changes no product code and no tests: a rule change, or the first-time setup, which may change several of them together. A code change that needs a CI workflow change lands the workflow change first, in its own pull request. A pull request that changes or deletes an existing test, golden or `verify` step names each one and why in its body. Its reviewer, where its lane has one, reads those first, and when it edits `verify` also runs `verify` from `main` (`review` says so too).
- **Lessons become tests first, and carry a trigger.** A confirmed failure gets a regression test. It becomes a lesson only when no test can catch it: one line under "Lessons" in `docs/superpowers/history.md` naming its trigger (the paths, or the kind of change, a diff shows), what to look for, and the failure behind it. Before it pushes, a session reads the lessons and acts only on those whose trigger its diff matches; a plan also carries the matching ones into its brief, as `review` says.
- **Prune.** Tests, `verify` steps, lessons and rules only grow unless someone trims them. Each retrospective removes the ones that no longer catch anything or that another check already covers, naming each one and why: rules and lessons in its rule-change pull request, tests in their own.
