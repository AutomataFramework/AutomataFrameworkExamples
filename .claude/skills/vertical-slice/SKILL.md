# Vertical slice

A game starts with a vertical slice: one short, playable path through the core loop, as good as it can be. Then the game grows one milestone at a time from the slice, which evolves by default.

## Setting up

- **Keys once.** The owner creates every key and secret one time, at setup, and is never asked for a new or changed one: that is a setup failure, so all of them are planned up front. Before setup, list every outside service the whole brief will use, through launch, and every endpoint each one will call, and give each key every permission on that list. Where a provider cannot grant that whole list with a narrower key, take its full ("All") scope rather than come back. One key per provider account serves every service that uses that provider, where nothing public can read it, so no service runs on a narrower key of its own. Each key gets the longest lifetime the provider allows, and the setup output says beside it when it expires; a leaked key is revoked and replaced at once, and that is not a setup failure. Setup is one script, run one time: it asks for each value, checks every key against every endpoint it will be used on, with a read or a dry run where the real call would create or spend, so setup costs nothing, saves nothing until every check passes, then puts each key in every place it must go. It says beside each key how broad it is, so the owner sees what they grant. A key asked for after setup, or made without a permission its service needs, sends the owner back, and that is the failure this rule stops.
- Inspect the current repository, branch, remotes, project files and CI first. Reuse the existing repository; the absence of a playable slice is not a reason to create another one.
- Determine the platform and repository visibility from the brief and existing project. Ask the owner only for missing choices. This kit assumes a browser game with Playwright playtests and screenshots; another platform needs a suitable playtest tool and screenshot method recorded in the brief and covered by its permissions.
- If no repository exists, create one with the `gh` CLI only within the authorized destination and visibility. If a repository exists, preserve its history, remotes and existing project configuration.
- Perform needed setup on a branch, adding only missing project structure and tracking files: `docs/superpowers/progress.md`, `history.md` and `docs/superpowers/roadmap.md`. Reuse suitable existing setup and run the `release` setup check. CI workflow changes retain lane 3 checks and require explicit or applicable standing permission, except first-time bootstrap as defined in CLAUDE.md. Merge required setup changes before the slice starts; skip a setup pull request when nothing changes.
- Setup is where a game loses its first day. Start from "CI and test machines" below instead of designing CI from scratch, and change a default only when a measured result shows it does not work.
- The owner's batch of commands is written once, complete and in order. A key or secret that is shown only once (an API key, a GitHub App's private key, a token) is named as such in the step that creates it, with every place it must go listed in that same step (a repo secret and the cloud environment's secret, for example), so the owner never has to make it again. Prefer commands that ask for the value, such as `gh secret set NAME` with no value. Every command handed to the owner uses `gh`, never plain `git`: a branch delete is `GH_PAGER=cat gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<branch>`. Every `gh api` command handed to the owner starts with `GH_PAGER=cat`: without it the answer opens in a pager, and the owner sees nothing to copy back or is stuck in it. The same holds after setup for owner steps that are not keys: a change that needs one lists every one the approved brief will need, the ones its deploy and its later steps need included, as one paste before the build starts, so the owner is asked once. A change that seems to need a new key first finds a way with the keys setup made; when there is none, it is reported as a setup failure, with one paste that covers everything still to come. Where a step has no CLI and must be done on a provider's web page, such as creating a token, the session checks the page's current field and permission names against the provider's documentation before writing the step. It also runs the paste itself with stand-in commands first, so it never prints success when a command failed. A diagnostic the owner must run is the same: one complete paste that says exactly what to copy back (which block of the output, from which line to which), tried first against a made-up failing case to see that it shows the failure. A command that filters out the very case it is looking for costs the owner a second trip.
- Some steps a cloud session cannot do, because the cloud proxy refuses them: deleting branches, reading or writing Actions secrets, variables and runners, and posting commit statuses. They go in the owner's batch, or in a CI job. Reading workflow runs and downloading their artifacts works.
- A private repo on GitHub's free plan has no branch protection, rulesets, auto-merge or merge queue, and the setup check reports them missing. Ask the owner once, at setup, for a standing permission to merge a pull request in the lanes named below once its required checks are green and its lane's reviews are done, and record it under "Standing permissions"; sessions then merge without asking and report after. With no merge queue, the session that merges runs the queue by hand (Lanes and merging in `release`), and its last step before the merge is to look at `main` again: it compares `main`'s head with the `main` commit the pull request records as tested. If `main` has moved since that run, it merges current `main` in and the checks run again on the result before it merges; if not, that run stands. This is only for the pull request about to merge, never for one that is waiting, and the permission never covers a merge tested against an older `main`. It covers lanes 1 and 2, and lane 3 changes to CI workflow files, to the gate's own code (the code that starts, checks and deletes pods, and the webhook service, whose redeploy from `main` on such a merge is inside this permission) and to the tools that build or pack the game, after their audits, and nothing wider. Every other lane 3 change (a release or tag, any other deploy or spend, a migration, a write of real data, a rule change) still needs the owner's word or its own named permission.

## CI and test machines

- On a public repo, the unit tests, lint, typecheck and build run on GitHub's runners, which are free there, and the smoke set runs on one GPU pod. On a private repo, GitHub's included minutes run out and anything past them is billed, so no job runs on GitHub's runners there, included minutes or not (when they run out, every run fails at its first job): CI runs on cloud pods billed by the minute, never on paid GitHub minutes, a monthly server or the owner's computer. A GPU comes from a cloud GPU pod. The monthly CI budget goes in the setup brief, and the gate refuses to start pods once it is spent. A workflow that was there before the gate keeps using GitHub's runners until it is moved, so setup moves or turns off every such job before anything else runs. The check: a test reads every workflow file and, on a private repo, fails on a job that runs on a GitHub-hosted label (such as `ubuntu-latest`). Trigger: a diff that adds or changes a workflow job.
- CPU pods run everything that does not render: install, typecheck, unit tests, build and audits. GPU pods run only what renders: browser specs that draw the game, screenshots and the frame budget.
- On a private repo, the gate on every pull request is the unit tests on a CPU pod plus one GPU check (the smoke set) on a GPU pod. The full browser suite is not part of the gate (see Where tests run in `release`).
- GitHub Actions runs the workflow, and each job that needs a machine starts its own pod, which registers a just-in-time self-hosted runner for that one job. A job that starts pods needs a runner itself, so on a private repo the first runner of a run is started from outside GitHub: the repo's webhook calls a small free service (a serverless function on a free plan, for example) that starts one lead pod per run for the jobs that decide, start and delete pods, and deletes it when the run ends. That service is redeployed from `main` by a CI job, so the owner sets it up once. A GitHub App on the account that owns the repo, installed on that repo only, mints the runner credential: fine-grained tokens do not work for a collaborator, and the App's tokens last an hour. The pod key is one repo secret, made once at setup with every permission the gate and its service will use (pods read and write, billing read, the catalogs read), or the provider's full scope where a restricted key cannot be given them all; the gate's service uses the same key. Use the provider's current API: check its docs for a retired version before building on one.
- Every outside credential a service uses (the pod key, a deploy token) gets a preflight at deploy time, the same checks setup ran: with the service's own key, it calls every endpoint the service uses, a read or a dry run where the real call would create or spend, and the deploy fails when any call is refused. Unit tests with stand-in APIs cannot see what a key is allowed to do. A key that lacks one permission is refused on one endpoint only: the fast path that needed it stops working, the run stays green and nobody notices. Trigger: a diff that adds a call to an outside API, or a new or replaced key.
- No silent fallbacks. When the gate skips a fast path or falls back to a slower one (an early pod start, a cache, a second machine type), the run says so with the reason, as a warning annotation or a line in the run summary, and its own retries are counted there too. A fallback nobody can see is a defect: the run stays green while the speed-up it was built for is gone.
- Pods start from a prebuilt public image that already holds the runner, the browsers and a warm package store, so a runner is online in one to two minutes.
- GPUs are picked from the catalog cheapest first, and stock changes by the hour. A pod whose runner is not online in time (a few minutes after the pod was made; the CI spec sets it) is replaced once, a CPU pod as well as a GPU pod, since a provider sometimes makes a pod and never runs it. When the second one is not online either, the job names each missing runner and pod, and the run fails at the time limit the CI spec sets instead of waiting for stock. The catalog answers 429 when several gates start at once and the runner-config call sometimes answers 500: the gate retries those calls itself. Those are infrastructure retries inside the gate; a test that passes on retry is still a defect.
- Every pod is deleted when its job ends (the lead pod when its run ends), also when the run fails or is cancelled. A pod left behind by a dead run still counts against the pod limit and blocks later runs, so the step that starts pods first deletes gate pods older than the longest run, and the code that deletes pods at a run's end is live before any run relies on it. A guard step fails a GPU job whose browser drew with software WebGL (SwiftShader). On Linux, Chromium draws with the GPU only with `--use-angle=vulkan --enable-features=Vulkan`.
- A gate on `pull_request_target` always runs `main`'s copy of the workflow, so a workflow change is tested on a throwaway base branch that holds a `pull_request` copy. Its check runs land on `main`'s commit, so the gate posts a commit status on the pull request's head commit, and the session that merges reads that status.
- The gate's settings that decide behaviour (which machine comes first, a limit, a time-out) live in tested code, and a change to one comes with a test that fails when the value is put back. A test that passes whichever value is set is not a test: a fallback test that never refuses the first choice still passes after the order is flipped. A test also parses every workflow file, since a file that does not parse runs no jobs and fails no pull request. This is behaviour in code; a plain settings file is still checked as Verification in `build` says.
- Screenshot baselines and goldens are taken on the CI machines' system (Linux), never on one person's Mac.
- CI artifacts stay small and short-lived: on a private repo the account's artifact storage is shared and limited, and when it is full every upload fails, on every pull request. Screenshots kept as evidence for people are saved in a modern lossy format such as WebP, after any pixel comparison has run on the originals, and checked once to see that small text stays sharp and that a contrast measured from the compressed picture matches the original. Other files a run uploads (screenshots excepted, see below) are only what a reviewer reads, with the shortest retention that still covers the review rounds and the owner's looks. A newer upload replaces the older sets that the same workflow uploaded under the same name for the same pull request, and nothing else: never another pull request's, never another workflow's, never when this run uploaded nothing (the old set is then the only evidence), and a cleanup that fails warns in the run summary without changing the run's verdict. It deletes only sets the workflow would make again if it ran again on that set's commit. The cleanup is a step in the workflow, so it arrives as a lane 3 change with its audits. Merging that audited step is the approval for its later runs and for nothing wider: any other artifact delete, or a delete by hand, stays lane 3 (Risk in CLAUDE.md). Goldens, baselines and art references are committed files, not artifacts, and keep their format. The check: a test reads the workflow and fails on an upload step with no retention set, and tests of the cleanup cover each of those cases. Trigger: a diff that adds or changes an artifact upload.
- On a private repo, artifact storage is counted as an average over the month: a delete stops further charges but does not bring the month's figure down, and once the account is over its included storage, every upload fails until the month resets. So screenshots, the largest uploads, go to an object store outside GitHub with a lifecycle rule that deletes each one a few hours after upload, and the run summary links them. They are short-lived by design: a reviewer or a screens page that needs them later re-runs the walk to make them again, and nothing keeps a longer copy. The screens page carries its own copies only until the owner has looked at it (Screens page in `visual-check`). Its key is one of the keys setup makes (Keys once). The check: a test reads the workflows and fails on a step that sends screenshots to GitHub's artifact storage. Trigger: a diff that adds or changes a screenshot upload. A public repo's artifact storage is free and has no limit, so there screenshots stay in GitHub's artifact storage, still uploaded small and short-lived as the bullet above says, and this check does not apply.
- A screenshot walk too long for one job's time cap is split into pieces on separate GPU pods, within the pieces set in Settings, so each piece fits its cap. The split is a list in tested code, and a test fails unless every page, device and, where the game has more than one, language is walked by exactly one piece: none missed, none twice. Trigger: a diff that adds a page, a device or a language to the walk, or changes the pieces.
- As a guide to scale, a unit-test job on a mid-size CPU pod takes a few minutes and costs a few cents, and a pull request's gate (unit tests and one GPU check) costs about ten cents. Hosts of one machine type differ in speed: the same tests on the same code can take three times as long on one host as on another. The checks pod keeps a second machine type as its fallback, and which one goes first is decided by many real runs, not two: a pair of runs can point the wrong way. Changing the order is not how a slow suite is fixed: when the spread comes from the host, a new order chases noise. The order changes only when many runs show one machine type is steadily slower or fails to start, and the lasting fix is the cost of the tests themselves (How code is written in `build`). Tests that start processes or watch files can time out together on a stalled host: that is recorded under "Flaky tests" as Verification in `build` says, with the processor the job printed, and the fix is a test that waits on the event (the process is ready, the change was seen) and not on the clock; a timeout is never raised just to get past it. The job's first step prints the processor it got, so a slow run is read from the log before anyone suspects the tests. A change made for speed is done when real runs show it: the timed step over several real runs before and after, with their run numbers, not a local replay with stand-in calls. A fast path can pass its tests and a dry run and still not fire on real runs. Read the month's spend from the provider's billing API before starting more work; it lags by a few minutes.

## Hosting the server

- A game with a server chooses its host and machine size at setup, and the monthly hosting budget goes in the setup brief beside the CI budget.
- Size: start on the host's smallest shared size and measure it with a load test of full rooms (every seat filled, a whole match). Move up only when that test misses a budget in the brief, such as tick time or memory. The size and its monthly price are written in the brief; a bigger size is spend outside the brief, so it is the owner's choice.
- Paid plan before launch: a host's free trial can stop every machine a few minutes after it starts, and the game goes down with no error in the deploy. The setup check reads the account's plan or billing state through the host's CLI or API; a missing payment method is the first step in the owner's batch, and the release refuses to deploy while the check fails.
- From the first release, two read-only jobs run in the cloud with the deploy key setup made: an uptime check that calls the server's health endpoint on a schedule and alerts the owner when it fails (below), and a scheduled log report that reads the host's machine events and logs (stops, restarts, exit codes, out of memory) and warns on the host's own stop messages, such as a trial limit. On a private repo they run as scheduled workflows on the same pods as the gate's jobs, one short CPU job each, or as a scheduled cloud task, never on GitHub's runners and never a pod started every few minutes; their monthly cost goes in the brief beside the hosting budget. Trigger: a diff that adds a server or changes its host or size, and the first release.
- **Alerts reach a person.** An alert is an issue on the game's repo, assigned to the owner and naming them, so the code host emails them: no paid email service, and no address stored anywhere. The CI's app or bot identity opens it, never the owner's own token, because the host sends nobody email about their own actions. One issue per outage: a repeat failure adds nothing, and recovery comments and closes it. The issue says what failed, since when, and the first command to run. Trigger: a diff that adds or changes an alert, and the first release.
- **A rollback button from the first release.** The release workflow has a rollback input from day one: one `gh workflow run` command puts back an earlier released build, chosen from the host's own list of releases. It swaps only the build and keeps today's machine size and settings, so it first checks that the old build fits them (its memory, for one) and speaks the same protocol as the live client, and refuses with the reason when it does not. It works while the server is down, since that is when it is needed, and a run that changes nothing ends red, never green. It is a release, so it is lane 3.

## Before launch

The first public release waits until each of these holds on the commit being released; the drills, the rollback and the alerts apply where the game has a server. The launch report gives the evidence for each.

- **The owner's launch checklist.** Every item in the Anti-Vibe Networking Audit, the Anti-Vibe Game Cybersecurity Audit and the Anti-Vibe Browser Game Audit (the prompts listed beside this kit) is marked pass, fail, not applicable or waiting, each with its evidence (a file and line, a test, a run or a screenshot) on that commit, in one audit file and one page the owner can read. A fail is fixed before launch or carries the owner's written waiver. Not applicable says why. Waiting names the outside piece it waits on, such as a feature of the platform the game is played on, and is reported as open, never as passed. Items that need a real device or the owner's own hands are the owner's to check: the report lists them for the owner and never marks them passed on the owner's behalf.
- **Failure drills.** The failure tests in those lists (kill the server mid-match, add latency, drop, duplicate and reorder messages, restart under load, exhaust connections) run against a throwaway copy of the server in the cloud, never production, and the game recovers each time with no manual cleanup. Each drill's result and run go in the audit file.
- **A rehearsed rollback.** The rollback button is pressed once on the live server, before launch while few people play: back to the previous release, the game checked, then forward again. It needs an earlier release to go back to, so it comes after at least two releases. It is a deploy, so it waits for the owner's named permission.
- **Alerts that work.** The alert is tested end to end once: the uptime check pointed at an address that is down opens the issue, the owner says the email arrived, and recovery closes it. Until the owner says so, it is reported as not confirmed.

## Making the slice

The slice inherits the limits in Settings; where the prompt below says to keep looping or not to fix a number of rounds, those limits win. A try is one round: build, judge, fix, and the critic judges the fix. A fix nobody judged is never reported as passing. Out of rounds with a blocking defect left, the slice is reported incomplete, with the bar reached, the evidence and what is open. Its builders and critics count toward the work-session limit and run within it. The bar is met when the checks the coordinator wrote down before the run (what the slice must do, on which devices and hardware, within what frame time) pass in a recorded playthrough, and there are no unresolved blocking defects against the agreed criteria (optional improvements are notes and do not hold it up). On a public repo no session can measure a frame-time budget on named hardware. The loop does not wait for it, but it still counts: the slice is reported as "frame time not measured, awaiting the owner's measurement", never as meeting the bar, with the steps for the owner to measure it by hand (see Where work runs in `release`). The finished result is approved with the owner's measured number, or with the owner's waiver written beside it.

The coordinator fills in the two blanks below, runs this prompt once, and tells the owner the bar it chose, in one sentence. It is Matt Shumer's Claude of Duty prompt, with the models added:

I want to run a Gauntlet Loop for this goal:

[GOAL]

Possible references or quality bars:

[OPTIONAL REFERENCES]

Choose the strongest concrete bar that an agent can actually inspect and compare its work against. If I have not supplied one, propose a useful comp or measurement that plays the same role for this task that real Call of Duty screenshots played for Matt Shumer's Claude of Duty game (read the prompt: https://github.com/mshumer/Claude-of-Duty/blob/main/prompt.md). Explain the bar in one sentence.

Then write a short prompt for Claude Code or Codex in the style of Matt's prompt (minimal is better here, we want the agent to decide the specifics!).

Give the lead agent the goal and the bar, but let it choose the approach. Tell it to divide the goal into the smallest pieces that can be improved and judged independently. For each important piece, it should fan out a builder and a separate critic with fresh context.

Each critic must inspect the real output, compare it directly with the bar—using a blind A/B comparison when possible—identify the biggest remaining gap, and send it back for another round. Keep looping until our output wins or I stop the run.

Have the lead agent send progress updates, early playable previews and material decisions to the coordinator, following the owner visibility rules.

The lead orchestrates. It runs on the model and effort Settings names for the slice lead, splits the work and writes a self-contained brief (goal, the files it owns, what it waits on, acceptance check, branch) for each builder and critic, and the coordinator starts each one as its own thread on the model and effort Settings names for its role. The lead's first step is sending builder briefs, not building. Do not prescribe the architecture, exact decomposition, or a fixed number of rounds. Keep the final prompt short, just like Matt's.

- `[GOAL]` is the game's one-line pitch and core loop, taken from the outcome in the owner's Start prompt; do not ask the owner for it again. `[OPTIONAL REFERENCES]` are the owner's reference games or screenshots, if any.
- The prompt writes a shorter prompt. The coordinator adds one line to the prompt it hands the slice session, so the limit travels with it: "Stop after N rounds and report the bar reached, the evidence and what is left", with N the slice rounds in Settings. That line wins over anything in the prompt about rounds.
- The slice session runs where it can run and play the game: a cloud session that plays and shoots the game on a cloud GPU pod, never with software rendering in the cloud container (see "Shoot on a GPU" in `visual-check`); never the owner's computer. Real input feel is judged by the owner by hand on the preview. Builders, critics and required reviews are separate threads, under the Delegation rule and session limits. The slice lead's builders count as writing code.
- The slice session is tracked like a stage: it reports to the coordinator, which keeps `progress.md`, one line per piece finished. The lead itself only reads and never writes code, but it takes one of the 3 code-writing places.
- The retrospective is the last stage of every slice, the first one included. After the slice ends, a fresh thread reviews every loop the slice ran (see "Retrospective" in `staged-path`), turns each lesson into a test where it can, and proposes the rest as one rule-change pull request for the owner to approve. Nothing to learn, no pull request. The next slice can start once the retrospective's pull request is open, or once the retrospective reports nothing to learn. Before it come the fresh end-to-end walk, the design review loop, the screens page and the owner's own walk (see "Slice end" in `staged-path`).
- **Delegation.** Use separate threads for the work and its reviews. The coordinator starts a fresh thread for each required code, design, visual or playtest review; it reads, runs checks and writes its audit file, and the implementer makes fixes. The slice lead asks the coordinator for its builder and critic threads. These threads count toward the work-session limits in Settings, and builders and the lead count toward the writer limit.

## From the slice to the game

- The slice is the game's first version, not a throwaway. When it is finished, the owner approves it as a finished result and the stages start, with the slice as the spec's starting point.
- It evolves by default. Assess it first: for each part, keep, refactor or replace, with a reason, written into the spec. Refactor or replace a part only for a constraint shown by evidence: a test it cannot take, a measured budget it misses, a defect its structure keeps causing. Code not fitting the folder layout alone never justifies replacing working gameplay; it moves into the layout as it is touched. Behavior is preserved by repeatable playthroughs and recorded parameters with their units (speeds per second, sizes in pixels or metres, timings in milliseconds), not by copying numbers alone.
- Before a part is replaced, the spec names a runnable baseline when one helps: a commit the playtest runs on, to compare the new part against.
- The coordinator and the owner agree a delivery order, with the advisor asked first: a short list of milestones in `docs/superpowers/decompositions/<date>-<topic>-delivery-order.md`. Milestone 0 is the slice. Each milestone gets its brief and follows the shared risk rules: work inside it takes the short or the staged path by its own risk, and independent pieces run side by side within the limits in Settings. Later work follows those shared paths; the Gauntlet prompt is not run again.
- `docs/superpowers/roadmap.md` lists everything left, in order, with who does each step (the owner or a session) and where it stands. The coordinator keeps it current. A milestone is done when it is merged to `main`, green there, its screens have been through the design review loop (`visual-check`), and the owner has approved the finished result.
